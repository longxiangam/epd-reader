## Introduction

The ESP32-C3 has only about 400KB of SRAM, yet it has to run the full WiFi + TCP/IP + TLS + HTTP stack. This article explains how the network stack is put together in this project: the WiFi driver, the HTTP/HTTPS request client, and the provisioning scheme with a self-built DHCP/DNS server in AP mode.

## 1. WiFi Driver Layer: from esp-wifi to esp-radio

### 1.1 Initialization

This project uses `esp-radio` 0.18 — the new crate in the esp-rs ecosystem that split the WiFi driver out of `esp-hal`. Compared to the old `esp-wifi` 0.7, the API changed dramatically but became simpler:

```rust
// src/wifi.rs:88-168
pub async fn connect_wifi(
    spawner: &Spawner,
    rng: Rng,
    wifi: esp_hal::peripherals::WIFI<'static>,
) -> Result<&'static Stack<'static>, WifiNetError> {
    // connect_wifi is called by main as the last step; if some task called
    // use_wifi earlier, we wait for REINIT_WIFI_SIGNAL before really initializing
    REINIT_WIFI_SIGNAL.wait().await;
    HAL_RNG.lock().await.replace(rng);   // hand the RNG to the world; TLS handshake needs it

    // Read the WiFi configuration from Flash
    let ssid = crate::storage::WIFI_INFO.lock().await.as_ref().unwrap().wifi_ssid.clone();
    let password = crate::storage::WIFI_INFO.lock().await.as_ref().unwrap().wifi_password.clone();

    // Configure Station mode
    let station_config = WifiConfig::Station(
        StationConfig::default()
            .with_ssid(ssid.as_str())
            .with_password(password.as_str().into()),
    );

    // One line creates the WiFi controller and the network interfaces
    let (controller, interfaces) = esp_radio::wifi::new(
        wifi,
        ControllerConfig::default().with_initial_config(station_config),
    ).unwrap();

    let wifi_interface = interfaces.station;
    // ...
}
```

Compare with the steps the old version required:
- ~~`esp_wifi::initialize(EspWifiInitFor::Wifi, timer, rng, radio_clk, &clocks)`~~
- ~~`esp_wifi::wifi::new_with_mode(&init, wifi, WifiStaDevice)`~~

The new version only needs one call, `esp_radio::wifi::new(wifi, config)`; there is no need to manually pass timers, RNG, radio clock, and so on. The WiFi peripheral comes from `Peripherals`, and ownership is transferred via function arguments.

### 1.2 The Network Stack: Stack / Runner Split

The biggest architectural change in embassy-net 0.9 is splitting the network stack into two parts:

```rust
// src/wifi.rs:119-130
let (stack, runner) = embassy_net::new(
    wifi_interface,
    Config::dhcpv4(Default::default()),  // DHCP obtains the IP automatically
    make_static!(StackResources::<4>::new()),  // up to 4 concurrent connections
    seed,  // random seed (generated by the hardware RNG)
);
let stack: &Stack<'static> = &*make_static!(stack);

spawner.spawn(net_task(runner).unwrap());   // Runner runs as an independent task
spawner.spawn(connection_wifi(controller).unwrap());
spawner.spawn(do_stop().unwrap());          // auto power-off after 30s idle
```

The **Stack** is the interface of the network stack, used to create sockets, query DNS, obtain the IP, etc.
The **Runner** is the engine of the network stack, driving TCP/IP processing in a dedicated task.

The benefit of this split: running the network stack does not consume the caller's execution time. The caller only works through the Stack interface, while protocol processing happens asynchronously in the background.

The runner task is trivial:

```rust
// src/wifi.rs:171-174
#[embassy_executor::task]
async fn net_task(mut runner: embassy_net::Runner<'static, Interface<'static>>) {
    runner.run().await
}
```

### 1.3 Waiting for the Link (with Timeouts)

```rust
// src/wifi.rs:133-164 (excerpt)
let init_start_secs = Instant::now().as_secs();
// Wait for the physical link, at most INIT_WAIT_TIMEOUT_SECS = 35 seconds
loop {
    if stack.is_link_up() { break; }
    if matches!(*WIFI_STATE.lock().await, Some(WifiNetState::WifiStopped)) {
        return Err(WifiNetError::TimeOut);   // stopped while waiting
    }
    if Instant::now().as_secs() - init_start_secs > INIT_WAIT_TIMEOUT_SECS {
        return Err(WifiNetError::TimeOut);
    }
    Timer::after(Duration::from_millis(1000)).await;
}

// Wait for DHCP to hand out an IP, with a 10-second grace period
loop {
    if let Some(config) = stack.config_v4() {
        println!("Got IP: {}", config.address);
        break;
    }
    if Instant::now().as_secs() - init_start_secs > INIT_WAIT_TIMEOUT_SECS + 10 {
        return Err(WifiNetError::TimeOut);
    }
    Timer::after(Duration::from_millis(500)).await;
}
```

A WiFi connection has two phases: first physical association (link up), then DHCP acquiring an IP address. Both phases are implemented with polling + `Timer::after` — under cooperative scheduling, polling does not block other tasks.

Unlike the early "wait forever" behavior, both phases now have time-based limits: `STACK_MUT` is not written until an IP is obtained, so `use_wifi` will not let any request through — when the network is unreachable at boot, the main flow immediately gets an `Err` and falls back to the offline path instead of hanging on the splash screen.

## 2. WiFi Lifecycle Management

WiFi is the biggest power consumer; the ESP32-C3 draws roughly 80-100mA with WiFi on and drops to the microamp level when it is off. The project therefore implements fine-grained WiFi lifecycle management.

### 2.1 State Machine

```rust
// src/wifi.rs:33-39
pub enum WifiNetState {
    WifiConnecting,   // connecting
    WifiConnected,    // connected
    WifiDisconnected, // disconnected
    WifiStopped,      // stopped (power-saving mode)
}
```

State transitions:

```
                     ┌──────────────┐
                     │  WifiStopped │ ← 30s without requests / 5 failed connect attempts
                     └──────┬───────┘
                            │ RECONNECT_WIFI_SIGNAL
                            ▼
  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │WifiDisconnected│─►│WifiConnecting │─►│WifiConnected │
  └──────────────┘   └──────────────┘   └──────┬───────┘
         ▲                                       │
         │ link lost                             │ STOP_WIFI_SIGNAL
         └───────────────────────────────────────┘
```

### 2.2 The Connection Management Task

The `connection_wifi` task maintains the WiFi connection:

```rust
// src/wifi.rs:176-266 (core logic simplified)
#[embassy_executor::task]
async fn connection_wifi(mut controller: WifiController<'static>) {
    let mut consecutive_failures: u32 = 0;
    loop {
        if controller.is_connected() {
            consecutive_failures = 0;
            WIFI_STATE.lock().await.replace(WifiNetState::WifiConnected);

            // Wait for a disconnect event or the stop signal
            loop {
                let mut subscriber = controller.subscribe().unwrap();
                let close_signal = STOP_WIFI_SIGNAL.wait();
                match select(subscriber.next_event_pure(), close_signal).await {
                    First(_) => {
                        // WiFi event (possibly a disconnect)
                        if !controller.is_connected() {
                            WIFI_STATE.lock().await.replace(WifiNetState::WifiDisconnected);
                            break;   // leave the inner loop, fall through to reconnect
                        }
                    }
                    Second(_) => {
                        // Stop signal received
                        STOP_WIFI_SIGNAL.reset();
                        let _ = controller.disconnect_async().await;
                        WIFI_STATE.lock().await.replace(WifiNetState::WifiStopped);
                        RECONNECT_WIFI_SIGNAL.wait().await;  // sleep until the reconnect signal
                        WIFI_STATE.lock().await.replace(WifiNetState::WifiDisconnected);
                        break;
                    }
                }
            }
        }

        // Re-read SSID/password from Flash before each attempt (network can change without reboot)
        // ... controller.set_config(&station_config) ...

        WIFI_STATE.lock().await.replace(WifiNetState::WifiConnecting);
        match controller.connect_async().await {
            Ok(_) => {
                consecutive_failures = 0;
                WIFI_STATE.lock().await.replace(WifiNetState::WifiConnected);
            }
            Err(e) => {
                consecutive_failures += 1;
                if consecutive_failures >= MAX_CONNECT_RETRIES {
                    // 5 consecutive failures: give up and set WifiStopped (equivalent to
                    // turning WiFi off), wait for RECONNECT_WIFI_SIGNAL — prevents
                    // spinning forever (and draining the battery) on a wrong password
                    let _ = controller.disconnect_async().await;
                    WIFI_STATE.lock().await.replace(WifiNetState::WifiStopped);
                    RECONNECT_WIFI_SIGNAL.wait().await;
                } else {
                    Timer::after(Duration::from_millis(CONNECT_RETRY_INTERVAL_MS)).await; // retry in 5s
                }
            }
        }
    }
}
```

The esp-radio 0.18 event listening API uses the `subscribe() + next_event_pure()` pattern, replacing the old `wait_for_event()`. It exposes all WiFi events instead of just one specific kind.

### 2.3 Automatic Shutdown

```rust
// src/wifi.rs:371-385
#[embassy_executor::task]
async fn do_stop() {
    loop {
        if let Some(WifiNetState::WifiConnected) = *WIFI_STATE.lock().await {
            // No request for 30 seconds AND no in-flight request holding the lock
            // before WiFi is shut down automatically
            if Instant::now().as_secs() - LAST_USE_TIME_SECS.lock().await.unwrap() > HOW_LONG_SECS_CLOSE
                && !*WIFI_LOCK.lock().await {
                STOP_WIFI_SIGNAL.signal(());
            }
        }
        Timer::after(Duration::from_millis(3000)).await  // check every 3 seconds
    }
}
```

### 2.4 The Network Lock: use_wifi / finish_wifi

Before making a network request you must "lock" WiFi so it is not shut down mid-use:

```rust
// src/wifi.rs:278-359 (simplified)
const TIME_OUT_SECS: u64 = 10;
/// Set to true during reading: blocks every use_wifi request (reading/networking mutual exclusion).
pub static WIFI_BLOCKED: AtomicBool = AtomicBool::new(false);

pub async fn use_wifi() -> Result<&'static Stack<'static>, WifiNetError> {
    // Networking is forbidden while reading (reading owns the memory; WiFi is off)
    if WIFI_BLOCKED.load(Ordering::Acquire) {
        return Err(WifiNetError::Using);
    }
    let secs = Instant::now().as_secs();
    // Wait for the lock, at most 10 seconds
    loop {
        if !*WIFI_LOCK.lock().await { break; }
        if Instant::now().as_secs() - secs > TIME_OUT_SECS {
            return Err(WifiNetError::TimeOut);
        }
        // Deliberately do NOT refresh "network last-used time" while waiting for the
        // lock: the lock holder refreshes it itself. Otherwise force_stop_wifi before
        // sleep would keep seeing "a request in flight" and never proceed.
        Timer::after(Duration::from_millis(500)).await;
    }
    *WIFI_LOCK.lock().await = true;  // acquire

    let result = use_wifi_locked(secs).await;
    if result.is_err() {
        *WIFI_LOCK.lock().await = false;  // release on failure too
        println!("use_wifi failed, wifi lock released");
    }
    result
}

async fn use_wifi_locked(secs: u64) -> Result<&'static Stack<'static>, WifiNetError> {
    if *WIFI_STATE.lock().await == None {
        REINIT_WIFI_SIGNAL.signal(());   // trigger init (no movement within 3s → WaitConnecting)
    }
    if WIFI_STATE.lock().await.unwrap() == WifiNetState::WifiStopped {
        RECONNECT_WIFI_SIGNAL.signal(()); // trigger reconnect
    }

    const WAIT_STACK_SECS: u64 = 30;
    loop {
        refresh_last_time().await;        // keep refreshing last-use while waiting
        unsafe {
            let stack = *core::ptr::addr_of!(STACK_MUT);
            if let Some(v) = stack {
                if v.is_link_up() {
                    v.wait_config_up().await;
                    return Ok(v);
                } else if beyond TIME_OUT_SECS {
                    return Err(WifiNetError::TimeOut);   // link not up within 10s
                }
            } else if beyond WAIT_STACK_SECS {
                // Cold boot / wake DHCP can take a dozen seconds; give up if STACK_MUT
                // is still unwritten
                return Err(WifiNetError::Infallible);
            }
        }
        Timer::after(Duration::from_millis(500)).await;
    }
}

pub async fn finish_wifi() {
    refresh_last_time().await;  // refresh last-used time
    *WIFI_LOCK.lock().await = false;  // release
}
```

Usage pattern:

```rust
// Typical usage
let stack = use_wifi().await?;           // get the network stack (WiFi is connected)
let client = RequestClient::new(stack).await;
let response = client.send_request(url).await?;
finish_wifi().await;                      // release (starts the 30-second countdown)
```

`WIFI_LOCK` is the serialization point for all network requests — only one request is in flight at any time, which is exactly why the `static mut` buffers in `request.rs` can safely take mutable references (single core + the lock). A few details worth noting:

- **Failure paths must release the lock**: every failure after `use_wifi` acquires the lock (init timeout, link timeout, stack not ready) releases it; otherwise all subsequent requests would deadlock forever, and the pre-sleep WiFi shutdown would hang too;
- Before sleep, `force_stop_wifi()` **never preempts** an in-flight request: it first waits for `WIFI_LOCK` to be released (a single request is bounded: ~10s waiting for the link + 10s socket timeout, so it always finishes within ~30s; 45s is the safety net), then sends the stop signal, rather than killing a request mid-socket-read. The 30-second idle check in `do_stop` also requires the lock to be free, because a socket blocked in a long `read` does not refresh the last-use time;
- When entering the reading page there is `force_stop_wifi_quick()`: it waits at most 3 seconds for in-flight requests before force-stopping WiFi (reading monopolizes memory and cannot wait longer), and returns even if the stop did not complete;
- `refresh_last_time()` only refreshes the "network last-used time", never the user activity time — otherwise background NTP retries would keep resetting the idle timer and the device could never decide it is idle enough to sleep.

## 3. The HTTP/HTTPS Client

### 3.1 The Request Client

`RequestClient` wraps HTTP/HTTPS **GET** requests:

```rust
// src/request.rs
pub struct RequestClient {
    stack: &'static Stack<'static>,
    rng: RngWrapper,   // taken from wifi::HAL_RNG; random source for the TLS handshake
}
```

What really consumes memory are the send/receive buffers. They are declared as `static mut` in `.bss` (not on the heap), and the `WIFI_LOCK` serialization guarantees exclusive use (single-core ESP32-C3 + only one request in flight at any time):

| Buffer | Size | Purpose |
|--------|------|---------|
| `RX_BUF / TX_BUF` | 4 KB each | TCP send/receive |
| `TLS_RX_BUF / TLS_TX_BUF` | 8 KB each | TLS send/receive (handshake records + encrypted traffic) |
| `HEADERS_BUF_` | 1 KB | Response headers |
| `RESPONSE_BUF_` | 8 KB | Response body (Sina daily K-line, 60 candles ≈ 6.4KB; minute data ≈ 5.8KB; weather/holiday < 4KB) |

About 33KB of static buffers in total. Moving them off the heap into `.bss` is what allows the heap to fit in a separate dram2 segment (~64KB, DRAM released by the bootloader) and leaves all of main DRAM to the call stack.

### 3.2 Three Send Variants and Custom Headers

```rust
// Copying variant: copies the body into a Vec (for callers with small, infrequent
// responses, such as IP location or weather)
pub async fn send_request(url: &str) -> Result<ResponseData, RequestError>

// Zero-copy variant: returns &'static [u8] pointing into RESPONSE_BUF_; contract —
// valid until the next send_request* call
pub async fn send_request_slice(url: &str) -> Result<&'static [u8], RequestError>

// Zero-copy with custom headers (e.g. Sina quotes require a Referer)
pub async fn send_request_slice_with(url: &str, headers: &[(&str, &str)])
    -> Result<&'static [u8], RequestError>
```

URLs are parsed internally: `https://` defaults to port 443, `http://` to 80, any other scheme returns `UnsupportedScheme`; an empty path becomes `/`. The `RequestError` enum covers DNS / connection / TLS / timeout / buffer overflow, and the stock page maps it to short Chinese strings for display.

Callers also wrap requests in `wifi::set_request_loading(true/false)` — the weather, calendar and stock pages use it to draw a "loading" indicator on screen so the user knows the device is online.

### 3.3 The HTTPS Request Flow

HTTPS adds a TLS layer on top of TCP (simplified):

```rust
// 1. DNS resolution
let ip_address = resolve(host).await?;
// 2. TCP connect (10s timeout)
let mut socket = TcpSocket::new(*stack, &mut RX_BUF, &mut TX_BUF);
socket.set_timeout(Some(Duration::from_secs(10)));
socket.connect((ip_address, port)).await?;
// 3. TLS handshake
let config = TlsConfig::new().with_server_name(host).enable_rsa_signatures();
let mut tls = TlsConnection::new(socket, &mut TLS_RX_BUF, &mut TLS_TX_BUF);
tls.open(TlsContext::new(&config,
    UnsecureProvider::new::<Aes128GcmSha256>(&mut rng))).await?;
// 4. GET request + read the response into RESPONSE_BUF_
let request = Request::get(path).host(host).headers(headers).build();
request.write_header(&mut tls).await?;
let response = Response::read(&mut tls, Method::GET, &mut HEADERS_BUF_).await?;
response.body().reader().read_to_end(&mut RESPONSE_BUF_).await?;
```

Note that TLS uses `UnsecureProvider` — **no certificate verification**. A full CA certificate chain needs several hundred KB of root certificates, more than the ESP32-C3 can spare; for non-sensitive data like weather/stocks this is an acceptable trade-off. The cipher suite is fixed to `Aes128GcmSha256` with RSA signatures enabled. All requests are GET (no POST/PUT).

Plain HTTP takes the same path minus step 3 (the TLS handshake), reusing the same `RX_BUF/TX_BUF`.

### 3.5 Weather and Holiday Data Sources

Weather and holidays are the only two families of periodic HTTP requests after boot; both are driven by the background `ntp_worker`: once time has synced at least once (`sync_time_success()`), the end of every worker cycle (time syncs every 3600 seconds) calls the sync entry points, which then use the "is the data stale" check to decide whether a real request is needed:

- **Weather** (`weather.rs`): by default the Seniverse `api.seniverse.com` 5-day forecast (token configurable on the provisioning page; a default key is built into the code); with the `weather-openmeteo` feature it switches to `api.open-meteo.com` (HTTPS + coordinate query). On success the data plus a sync timestamp are written to `WeatherStorage` (Flash); the next wake-up reads the cache straight from Flash;
- **Freshness**: data older than 5 hours counts as stale (`weather_stale()` / `stale_in_secs()`). A scheduled wake-up checks this first — if the data is still fresh, the device doesn't even go online; it redraws from the local cache and goes back to sleep immediately;
- **Holidays** (`HolidayInfo` in `weather.rs`): the source is the yearly JSON from `NateScarlet/holiday-cn` on GitHub. Direct connections to `raw.githubusercontent.com` from within China are blocked by SNI (the TLS handshake is reset immediately, appearing as `TlsError(Io(ConnectionReset))`), so it tries a **three-level URL fallback**:

```rust
// src/weather.rs:224-228
let urls = [
    format!("https://cdn.jsdelivr.net/gh/NateScarlet/holiday-cn@master/{}.json", current_year),
    format!("https://fastly.jsdelivr.net/gh/NateScarlet/holiday-cn@master/{}.json", current_year),
    format!("https://raw.githubusercontent.com/NateScarlet/holiday-cn/master/{}.json", current_year),
];
// Tried in order; the first success wins; the last error is printed if all fail
```

The first two are jsDelivr CDN mirrors of the same data (reachable from China); the last falls back to the GitHub origin (still usable for devices abroad). The whole request is wrapped in `set_request_loading(true/false)`; a parse failure (possibly 429 rate limiting) prints the raw response for diagnosis; success records the update time in `SyncStampStorage` for the settings page.

## 4. AP Mode and Provisioning

On first use the device has no WiFi configuration (`wifi_finish == false`). It then enters AP (Access Point) mode, creating a hotspot named "esp_wifi"; the phone connects to it and configures the WiFi credentials through a web page.

### 4.1 AP Mode Initialization

```rust
// src/wifi.rs:428-498 (simplified)
pub async fn start_wifi_ap(spawner: &Spawner, rng: Rng, wifi: ...) {
    let ap_config = WifiConfig::AccessPoint(
        AccessPointConfig::default().with_ssid("esp_wifi")
    );

    let (controller, interfaces) = esp_radio::wifi::new(wifi, config)?;
    let wifi_ap_interface = interfaces.access_point;

    // AP mode uses a static IP (no DHCP)
    let ap_net_config = Config::ipv4_static(StaticConfigV4 {
        address: Ipv4Cidr::new(Ipv4Address::new(192, 168, 2, 1), 24),
        gateway: Some(Ipv4Address::new(192, 168, 2, 1)),
        dns_servers: Default::default(),
    });

    let (ap_stack, runner) = embassy_net::new(wifi_ap_interface, ap_net_config, ...);
    spawner.spawn(ap_task(runner)).unwrap();            // network stack Runner
    spawner.spawn(dhcp_service()).unwrap();  // self-built DHCP service
    spawner.spawn(dns_service()).unwrap();   // self-built DNS service
    spawner.spawn(connection_wifi_ap(controller)).unwrap();
}
```

The AP stack is stored separately in `AP_STACK_MUT`, independent of `STACK_MUT` in STA mode. Which mode applies is decided by `WIFI_MODEL` (`WifiModel::AP / STA`): provisioning boot uses AP, normal boot uses STA.

### 4.2 The Self-Built DHCP Service

In AP mode there is no ready-made DHCP server. The project implements the core of the DHCP protocol by hand over a UDP socket bound to port 67:

```rust
// src/wifi.rs:534-596 (simplified)
#[embassy_executor::task]
async fn dhcp_service() {
    let mut udp_socket = UdpSocket::new(*ap_stack, ...);
    udp_socket.bind(67);  // DHCP service port

    loop {
        match udp_socket.recv_from(&mut buf).await {
            Ok((n, src)) => {
                let msg = Message::new(buf).unwrap();
                let options = v4_options!(msg; MessageType required, ...);
                match options {
                    Ok((msg_type, _, _)) => {
                        if msg_type == MessageType::DISCOVER {
                            send_dhcp_offer(&udp_socket, src, &msg).await;
                        } else if msg_type == MessageType::REQUEST {
                            send_dhcp_ack(&udp_socket, src, &msg).await;
                        }
                    }
                    _ => {}
                }
            }
            _ => {}
        }
    }
}
```

DHCP allocation policy:
- Allocated IP: `192.168.2.2`
- Gateway: `192.168.2.1` (the ESP32 itself)
- DNS: `192.168.2.1` (the ESP32 itself)
- Lease time: 3600 seconds

The `dhcparse` crate parses and builds DHCP packets, avoiding hand-rolled binary protocol handling.

### 4.3 The DNS Hijacking Service

So that the provisioning page opens no matter what domain the user types, the DNS service hijacks every query:

```rust
// src/wifi.rs:675-746 (simplified)
#[embassy_executor::task]
async fn dns_service() {
    let mut udp_socket = UdpSocket::new(*ap_stack, ...);
    udp_socket.bind(53);  // DNS service port

    loop {
        match udp_socket.recv_from(&mut buf).await {
            Ok((n, src)) => {
                // No matter what domain is queried, answer with the ESP32's own IP
                let response = create_dns_response(LOCAL_IP, &buf[..n]);
                udp_socket.send_to(&response, src).await;
            }
            _ => {}
        }
    }
}

fn create_dns_response(ip: Ipv4Addr, request: &[u8]) -> Vec<u8, 512> {
    let mut response = Vec::new();
    response.extend_from_slice(&request[0..2]).unwrap();  // transaction ID
    response.extend_from_slice(&[0x81, 0x80]).unwrap();   // flags: standard response
    // ... copy the query, append the answer (TTL 60s, A record) ...
    response.extend_from_slice(&ip.octets()).unwrap();    // the ESP32's IP
    response
}
```

This means any URL typed into the phone's browser (e.g. `www.baidu.com`) resolves to the ESP32's IP `192.168.2.1`, opening the provisioning page — a common Captive Portal technique.

## 5. The Web Provisioning Service

The provisioning service listens on TCP port 80 in AP mode and serves a web page plus a REST API. It can also run in STA mode: the QR-code screen of the settings page starts/stops it on demand, using the `STOP_WEB_SERVICE` signal to gracefully break out of the accept loop:

```rust
// src/web_service.rs:44-134 (simplified)
async fn web_tcp_socket(stack: &'static Stack<'static>) {
    let mut socket = TcpSocket::new(*stack, &mut rx_buffer, &mut tx_buffer);  // 1536B each
    loop {
        // select between accept and the stop signal: the signal ends the loop cleanly
        select(STOP_WEB_SERVICE.wait(), socket.accept(...)).await;

        // Keep-alive: serve multiple HTTP requests over one TCP connection
        loop {
            // 1) read until \r\n\r\n (end of headers)
            // 2) parse Content-Length, keep reading the body, then hand off to process_http
            process_http(&mut socket, &buffer[..pos]).await;
        }
        socket.close();
    }
}
```

Supported API:

| Path | Method | Function |
|------|--------|----------|
| `/`, `/index.html` | GET | Returns the provisioning HTML page (`files/config.html`, `Cache-Control: no-store`) |
| `/config` | GET | Returns the full configuration JSON (wifi / weather / sleep / display / stocks / reading / home_page) |
| `/configure_wifi` | POST | Saves the WiFi config; calls `software_reset()` only if the SSID or password **actually changed** |
| `/configure_weather` | POST | Saves the weather token / city |
| `/configure_sleep` | POST | Saves the reading / calendar sleep durations |
| `/configure_display` | POST | Saves the full-refresh interval (clamped to 1..=100; out-of-range falls back to the platform default) |
| `/configure_stock` | POST | Saves up to 6 (code, name) stock pairs (`code0..code5` / `name0..name5`) |
| `/configure_reading` | POST | Saves reading layout: font size px (12..=40), line gap (-10..=10), rotation (0..3), font file name |
| `/books` | GET | Lists e-books in the SD card's `books` directory (streamed JSON, one name at a time) |
| `/images` | GET | Lists images in the SD card's `images` directory |
| `/upload?name=XX&chunk=N` | POST | Chunked e-book upload (URL-encoded Chinese long file name, decoded via `url_decode`, created as LFN) |
| `/upload_image?name=XX&chunk=N` | POST | Chunked image upload |
| `/delete` | POST | Deletes an e-book (together with legacy `.idx` and the `.log` progress file) |
| `/delete_image` | POST | Deletes an image |
| `/sleep_image` | GET | Queries the standby wallpaper state (`flash_sleep` partition, returns size) |
| `/upload_sleep_image` | POST | Uploads the standby wallpaper (30KB limit, written to Flash) |
| `/delete_sleep_image` | POST | Deletes the standby wallpaper |

All JSON responses carry `Content-Length` and `Connection: keep-alive` headers. Form parsing (`parse_form`, multipart/form-data) supports up to 20 fields and reads the body across TCP segments according to `Content-Length` — a fix made for the large multi-stock form so fields are no longer dropped when the body arrives in segments. File upload supports chunking to cope with the device's small TCP buffers: `chunk=0` creates the file with `ReadWriteCreateOrTruncate`, later chunks append with `ReadWriteCreateOrAppend`; the chunk index comes in via the URL parameter `chunk=N`, and any body bytes that already arrived with the header are written to disk before reading more from the socket, so no bytes are lost.

The key to upload/delete is **Chinese long file names**: the name is first `url_decode`d, then the forked `embedded-sdmmc`'s `open_long_name_file_in_dir` creates the file directly by long name (see Part 6).

## Summary

| Topic | Key Point |
|-------|-----------|
| WiFi driver | `esp-radio` 0.18, one-call `wifi::new()` initialization |
| Network stack | embassy-net 0.9, Stack/Runner split |
| WiFi lifecycle | 4 states + Signal-driven transitions; timeouts throughout init and connect |
| Connect retries | Gives up after 5 consecutive failures into `WifiStopped`, retries on signal |
| Auto power saving | WiFi off after 30s without requests (not while a request holds the lock) |
| HTTP | reqwless 0.14, GET requests, ~33KB of static `.bss` buffers |
| HTTPS | embedded-tls 0.18, AES-128-GCM, certificate verification skipped |
| IP location | myip.ipip.net (HTTPS, reachable in China, returns a city name) |
| Holiday source | Two jsDelivr CDNs → GitHub origin, three-level URL fallback |
| AP provisioning | Self-built DHCP + DNS hijacking (Captive Portal) |
| Web service | TCP port 80, keep-alive, chunked upload, AP/STA dual mode |

Implementing the full WiFi + TCP/IP + TLS + HTTP stack on an ESP32-C3 with only 400KB of SRAM owes a great deal to Embassy's async architecture — it keeps network operations from blocking the UI, and the fine-grained WiFi lifecycle management preserves battery life.
