## 引言

电子墨水屏（E-Paper Display，EPD）是一种非常特殊的显示技术。它不像 LCD 或 OLED 那样主动发光，而是通过电场控制微胶囊中带电颜料的移动来呈现图像。它的核心优势是：**断电后画面不消失**——这正是电子书阅读器选择它的原因。

但这个特性也带来了独特的工程挑战：刷新速度慢（几百毫秒到数秒）、有"鬼影"问题、刷新策略需要精心设计。本文将从驱动层到渲染架构，完整解析本项目如何驾驭电子墨水屏。

## 1. 电子墨水屏的工作原理

### 1.1 基本原理

电子墨水屏的每个像素包含一个透明微胶囊，里面有带正电的白色粒子和带负电的黑色粒子。施加正电压时，白色粒子移到顶部，像素显示白色；施加负电压则相反。

这意味着：
- **保持画面不需要耗电**——粒子停留在原位
- **改变画面才需要耗电**——需要施加电压移动粒子
- **刷新有延迟**——粒子物理移动需要时间

### 1.2 全刷与局部刷新

本项目使用的 Waveshare 电子墨水屏支持两种刷新模式：

| 模式 | 耗时 | 特点 |
|------|------|------|
| **Full（全刷）** | ~2-3 秒 | 黑白交替闪烁，完全清除残影 |
| **Quick（局部刷新）** | ~0.3 秒 | 不闪烁，但会积累鬼影 |

鬼影（Ghosting）是电子墨水屏特有的问题：上次显示的内容会隐约残留在新画面上。局部刷新虽然快，但每刷新几次就需要做一次全刷来清除鬼影。

## 2. 屏幕驱动层

### 2.1 条件编译选择屏幕

项目通过 feature flags 支持多种屏幕尺寸，在 `display.rs` 中通过类型别名统一抽象：

```rust
// src/display.rs:33-46
#[cfg(feature = "epd2in9")]
pub type EpdDisplay = Display2in9;          // 296×128 像素
#[cfg(feature = "epd2in9")]
pub type EpdControl<SPI, BUSY, DC, RST, DELAY> = Epd2in9<SPI,  BUSY, DC, RST, DELAY>;

#[cfg(feature = "epd4in2")]
pub type EpdDisplay = Display4in2;          // 400×300 像素（驱动来自 epd4in2_v3 模块）
#[cfg(feature = "epd4in2")]
pub type EpdControl<SPI, BUSY, DC, RST, DELAY> = Epd4in2<SPI, BUSY, DC, RST, DELAY>;

#[cfg(feature = "epd2in7")]
pub type EpdDisplay = Display2in7;          // 264×176 像素
```

屏型与板型 feature 由 `src/board/mod.rs` 守卫：三选一屏型（epd2in9 / epd2in7 / epd4in2）+ 二选一板型（board_v1 / board_v2），编译期固定全部 IO 分配。上层代码统一使用 `EpdDisplay` 和 `EpdControl` 类型，不需要关心具体的屏幕型号。切换屏幕只需修改编译参数。

### 2.2 屏幕初始化

屏幕驱动通过 `epd-waveshare` crate（自定义 fork：`longxiangam/epd-waveshare-modify`）实现。EPD 控制器在渲染任务中完成初始化：

```rust
// src/display.rs:114-131
#[embassy_executor::task]
pub async fn render(
    mut spi_device: &'static mut ActualSpi<'static>,
    busy: Input<'static>,
    rst: Output<'static>,
    dc: Output<'static>,
)
{
    // 由调用方（main）按 feature 构造好 GPIO 驱动再传入，本任务不绑定具体引脚号
    let mut epd = EpdControl::new(&mut spi_device, busy, dc, rst, &mut embassy_time::Delay).unwrap();
    let mut display: EpdDisplay = EpdDisplay::default();
    display.clear_buffer(Color::White);

    let receiver = RENDER_CHANNEL.receiver();
    let quickly_lut = QUICKLY_LUT_CHANNEL.receiver();
    unsafe {
        core::ptr::addr_of_mut!(DISPLAY).write(Some(display));
    }
    // ...
}
```

GPIO 驱动在 `main` 里构造完成后传给渲染任务：

```rust
// src/main.rs:274-280
let epd_busy_in = Input::new(
    epd_busy,
    esp_hal::gpio::InputConfig::default().with_pull(Pull::Down),
);
let epd_rst_out = Output::new(epd_rst, Level::High, OutputConfig::default());
let epd_dc_out = Output::new(epd_dc, Level::High, OutputConfig::default());
spawner.spawn(display::render(spi_bus_epd, epd_busy_in, epd_rst_out, epd_dc_out).unwrap());
```

EPD 控制器需要 4 个 GPIO（两代板相同，定义在 `src/board/mod.rs`）：
- **BUSY**（GPIO6，下拉输入）：屏幕忙状态信号（屏幕在刷新时拉高，完成后拉低）
- **RST**（GPIO7）：复位信号
- **DC**（GPIO20）：数据/命令选择信号
- **CS**（GPIO3）：片选，数据传输通过前面讲的共享 SPI 总线

初始化完成后，帧缓冲区被存入全局 `static mut DISPLAY`，供页面代码绘制使用。

### 2.3 SPI 设备类型

EPD 使用的 SPI 设备类型在 esp-hal v1.x 下是这样定义的：

```rust
// src/display.rs:83
type ActualSpi<'a> = CriticalSectionDevice<'a, Spi<'a, esp_hal::Blocking>, Output<'a>, embedded_hal_bus::spi::NoDelay>;
```

这个类型看起来复杂，但拆解后很清晰：
- `CriticalSectionDevice`：带临界区互斥的 SPI 设备（上一篇文章详解过）
- `Spi<'a, esp_hal::Blocking>`：阻塞模式的 SPI 总线
- `Output<'a>`：CS 片选引脚
- `NoDelay`：不需要 CS 到数据之间的延迟

## 3. 生产者-消费者渲染架构

### 3.1 架构设计

本项目最大的架构亮点之一是显示系统的**解耦设计**。页面代码不直接操作屏幕硬件，而是通过 Channel 发送渲染请求：

```
┌──────────────┐    RENDER_CHANNEL    ┌──────────────┐    SPI    ┌─────────┐
│  页面 (Pages) │ ──── RenderInfo ──► │ render task  │ ────────► │ EPD 屏幕 │
│  (生产者)      │                      │ (消费者)      │           │         │
└──────────────┘                       └──────────────┘           └─────────┘
```

Channel 的定义：

```rust
// src/display.rs:74-75
pub static RENDER_CHANNEL: Channel<CriticalSectionRawMutex, RenderInfo, 64> = Channel::new();
pub static QUICKLY_LUT_CHANNEL: Channel<CriticalSectionRawMutex, bool, 64> = Channel::new();
```

渲染请求携带的信息：

```rust
// src/display.rs:28-31
pub struct RenderInfo{
    pub time:i32,
    pub need_sleep:bool,
}
```

### 3.2 为什么这样设计？

**解耦页面和硬件**。页面代码只需要：绘制到帧缓冲区 → 发送渲染请求。它不需要知道 SPI 总线的存在，不需要知道屏幕是否在忙，也不需要等待屏幕刷新完成。

**避免阻塞**。电子墨水屏的刷新耗时几百毫秒到几秒。如果页面代码直接等待刷新完成，整个 UI 逻辑会被阻塞。通过 Channel，页面代码在发送请求后立即返回，可以继续处理下一个事件。

**串行化访问**。Channel 保证同一时间只有一个渲染请求被处理，避免了多个页面同时操作屏幕的冲突。

### 3.3 页面如何绘制？

页面代码的渲染流程如下（以阅读页 `src/pages/read/page.rs` 的 `render()` 为例）：

```rust
// 典型的页面渲染流程（简化）
async fn render(&mut self) {
    if self.need_render {
        self.need_render = false;
        if let Some(display) = display_mut() {       // 获取帧缓冲区
            display.clear_buffer(Color::White);      // 清屏

            // 使用 embedded-graphics 绘制（文字 / 列表 / 进度条 …）
            list_widget.draw(display);

            // 矢量字体渲染正文（见第 10 篇）
        }

        // 发送渲染请求（阅读页刷完即睡 → need_sleep: true）
        RENDER_CHANNEL.send(RenderInfo { time: 0, need_sleep: true }).await;
    }
}
```

`display_mut()` 返回帧缓冲区的可变引用，页面可以自由绘制。绘制完成后通过 `RENDER_CHANNEL.send()` 通知渲染任务。

### 3.4 渲染任务：消费者的工作

渲染任务在独立 Embassy task 中运行，循环等待渲染请求：

```rust
// src/display.rs:142-245（核心逻辑简化，非 2.7 寸路径）
loop {
    let render_sign = receiver.receive();           // 等待渲染请求
    let quickly_lut = quickly_lut.receive();        // 或刷新模式切换

    match select(render_sign, quickly_lut).await {
        Either::First(render_info) => {
            // 标记"刷新周期进行中"——睡眠/断电前要等它清零（见 3.7）
            RENDER_BUSY.store(true, Ordering::Relaxed);
            add_render_times();                     // 渲染计数 +1

            // 屏幕若在睡眠，先唤醒（2.7 寸还要重建基准帧）
            if is_sleep {
                epd.wake_up(&mut spi_device, &mut embassy_time::Delay);
                is_sleep = false;
            }

            let buffer = unsafe {
                (*core::ptr::addr_of_mut!(DISPLAY)).as_mut().unwrap().buffer()
            };

            // 检查是否需要全刷（非 2.7 寸路径）
            let need_clear = take_need_clear();     // 冷启动/按键唤醒首帧为 true
            let need_force_full = (get_render_times() % get_full_refresh_times() == 0 || need_clear)
                && refresh_lut == RefreshLut::Quick;
            if need_force_full {
                spi_device = set_refresh_mode(RefreshLut::Full, &mut epd, spi_device);
            }

            // 将帧缓冲区数据发送到屏幕（发出 MasterActivation 后即返回，不等 BUSY）
            epd.update_and_display_frame(&mut spi_device, buffer, &mut embassy_time::Delay)
                .expect("render failed");

            // 异步等待物理刷新完成：每 2ms 轮询 BUSY，期间让出 executor
            wait_refresh_done(&mut epd).await;

            if need_force_full {
                // 必须等刷新完成再切回 Quick LUT
                spi_device = set_refresh_mode(RefreshLut::Quick, &mut epd, spi_device);
            }

            // 如果需要，让屏幕进入睡眠
            if render_info.need_sleep {
                is_sleep = true;
                epd.sleep(&mut spi_device, &mut embassy_time::Delay);
            }

            RENDER_BUSY.store(false, Ordering::Relaxed);
        },
        Either::Second(v) => {
            // 切换刷新模式（Quick = true / Full = false）
            RENDER_BUSY.store(true, Ordering::Relaxed);
            refresh_lut = if v { RefreshLut::Quick } else { RefreshLut::Full };
            spi_device = set_refresh_mode(refresh_lut, &mut epd, spi_device);
            RENDER_BUSY.store(false, Ordering::Relaxed);
        },
    }
    Timer::after(Duration::from_millis(50)).await;  // 等待稳定，继续循环
}
```

这里有个关键改动：**刷新等待是异步的**。驱动发出刷新命令后并不自旋等 BUSY 拉低，而是由 `wait_refresh_done()` 每 2ms 轮询一次、每次用 `Timer::after` 让出 executor——局部刷新的几百毫秒、全刷的几秒里，按键扫描、下一页栅格化等任务都能并发推进，而不是把整个单线程 executor 锁死。

### 3.5 刷新策略

系统维护一个渲染计数器，每 N 次局部刷新后强制全刷一次以清残影。N 的**平台默认值**是编译期常量（2.7 寸屏 20 次，其余 5 次），但可以在运行时被设置页 / Web 配置覆盖：

```rust
// src/display.rs:86-95
#[cfg(feature = "epd2in7")]
pub const DEFAULT_FULL_REFRESH_TIMES: u32 = 20;
#[cfg(not(feature = "epd2in7"))]
pub const DEFAULT_FULL_REFRESH_TIMES: u32 = 5;

// 运行时缓存（0 表示尚未加载，回退到平台默认）
static mut FULL_REFRESH_TIMES: u32 = 0;
```

`FULL_REFRESH_TIMES` 从 Flash 的 `DisplayStorage.full_refresh_times` 加载，并由 `reload_full_refresh_times()` 钳制到 `1..=100`——这步钳制是必须的，旧固件下该分区可能是 Flash 原始字节（0 或超大值），而全刷判定用到了计数与 N 的整除（N=0 会触发整除零 panic）。设置页与 Web 端修改后会立即调用 `reload_full_refresh_times()` 刷新缓存。

```rust
// src/display.rs:100-106
pub fn reload_full_refresh_times() {
    let raw = crate::storage::DisplayStorage::read().map(|d| d.full_refresh_times).unwrap_or(0);
    let v = if (1..=100).contains(&raw) { raw } else { DEFAULT_FULL_REFRESH_TIMES };
    unsafe { core::ptr::addr_of_mut!(FULL_REFRESH_TIMES).write(v); }
}
```

全刷判定按屏型分两种：
- **非 2.7 寸**：`get_render_times() % get_full_refresh_times() == 0`（计数到倍数即全刷）
- **2.7 寸**：`get_render_times() >= get_full_refresh_times()`，全刷后调用 `reset_render_times()` 归零（基准帧语义，见 3.6）

渲染计数器本身存储在 RTC 内存中，深度睡眠唤醒后仍然保持：

```rust
// src/display.rs:49-50
#[ram(unstable(rtc_fast))]
static mut RENDER_TIMES:u32 = 0;
```

此外还有一个冷启动清屏标记 `NEED_CLEAR`（rtc_fast，初值为 true，首次渲染后由 `take_need_clear()` 复位为 false）。它在两处被置位：

1. 上电冷启动：rtc_fast 段回到初值 true；
2. 非定时唤醒（按键/复位）进入程序：`main` 的唤醒分类处显式调用 `mark_need_clear()`：

```rust
// src/main.rs:188-192
// 非定时唤醒（按钮/上电）进入程序：首帧强制全刷，清上一会话残影；
// 定时唤醒保持快刷（分钟级唤醒每次全刷会闪烁+耗电）。
if !timed_wake {
    crate::display::mark_need_clear();
}
```

深睡唤醒（定时）不会触碰它，所以分钟级的定时唤醒保持快刷（闪烁小、省电）；只有真正冷启动或用户按键唤醒的 第一帧 才会强制一次全刷清残影。

### 3.6 2.7 寸屏的特殊处理

2.7 寸屏幕的局部刷新机制与众不同——它需要维护一个"旧帧"引用来计算差分。但在深度睡眠中，屏幕控制器的 RAM 会丢失，唤醒后第一帧必须重新建立基准。

```rust
// src/display.rs:60-65
#[cfg(feature = "epd2in7")]
static mut PREV_BUFFER: [u8; 5808] = [0xFF; 5808];  // 上一帧的备份
#[cfg(feature = "epd2in7")]
static mut PREV_BUFFER_VALID: bool = false;           // 是否有有效的旧帧
```

渲染时的三分支逻辑：

```rust
// src/display.rs:161-201（简化）
let render_count = get_render_times();
let need_force_full = render_count >= get_full_refresh_times() && refresh_lut == RefreshLut::Quick;

if refresh_lut == RefreshLut::Quick {
    if need_force_full {
        // 周期性全刷清残影：set_base_map 重建基准帧，计数归零
        epd.set_base_map(&mut spi_device, buffer, &mut embassy_time::Delay).expect("render failed");
        need_base_map = false;
        reset_render_times();
    } else if need_base_map {
        // 唤醒后或首次开机：有旧帧走静默过渡（不闪烁），没有旧帧必须全刷
        let prev_valid = unsafe { core::ptr::addr_of!(PREV_BUFFER_VALID).read() };
        if prev_valid {
            let prev = unsafe { &*core::ptr::addr_of!(PREV_BUFFER) };
            epd.set_base_map_quiet(&mut spi_device, prev, buffer, &mut embassy_time::Delay).expect("render failed");
        } else {
            epd.set_base_map(&mut spi_device, buffer, &mut embassy_time::Delay).expect("render failed");
        }
        need_base_map = false;
    } else {
        // 正常局部刷新
        epd.update_and_display_frame_partial(&mut spi_device, buffer, &mut embassy_time::Delay).expect("render failed");
    }
    // 先保存当前帧，再异步等 BUSY——保存与上传之间没有 await，页面任务改不了
    // DISPLAY；等 BUSY 期间页面才可能绘制下一帧，但本次画面已存入 PREV_BUFFER
    unsafe {
        (*core::ptr::addr_of_mut!(PREV_BUFFER)).copy_from_slice(buffer);
        core::ptr::addr_of_mut!(PREV_BUFFER_VALID).write(true);
    }
    wait_refresh_done(&mut epd).await;
}
```

这个设计非常精妙：通过在 RAM 中保存上一帧的备份，唤醒后可以做一次"静默"的基准帧设置，避免全刷时的闪烁。`need_base_map` 在唤醒（`wake_up` 之后）和手动切换刷新模式（`QUICKLY_LUT_CHANNEL` 消息）时都会被重新置位，保证下一条渲染请求重建基准。

### 3.7 渲染周期的边界：RENDER_BUSY 与 await_render_idle

渲染异步化后，刷新期间 executor 会调度其它任务——这意味着系统睡眠/断电代码可能恰好在面板刷新到一半时执行。若此时切断 EINK 电源或进深睡，面板会被留在半驱动状态，产生"发灰"的睡眠残影（需全刷才能清除）。

为此渲染任务用 `RENDER_BUSY`（AtomicBool）标记周期的起止，并暴露一个等待函数：

```rust
// src/display.rs:249-261
pub async fn await_render_idle() {
    loop {
        let busy = RENDER_BUSY.load(Ordering::Relaxed);
        let pending = !RENDER_CHANNEL.is_empty();
        if !busy && !pending {
            break;
        }
        Timer::after(Duration::from_millis(2)).await;
    }
}
```

系统进深睡前（`to_sleep_tips` / `reboot_sleep`）都会先 `await_render_idle().await`——既要等当前周期走完，也要把队列里排队的渲染请求排空，然后才切电源轨、写睡眠寄存器。

## 4. 帧缓冲区与 embedded-graphics

### 4.1 帧缓冲区

电子墨水屏的帧缓冲区是一个字节数组，每个 bit 代表一个像素（0 = 白，1 = 黑）。以 2.9 寸屏为例：

```
296 × 128 像素
= 296 × 128 / 8 字节
= 4736 字节 (约 4.6KB)
```

4.2 寸屏的帧缓冲区更大：400 × 300 / 8 = 15000 字节（约 14.6KB）。在 400KB SRAM 的 ESP32-C3 上，这是一笔不小的内存开销。

### 4.2 embedded-graphics 绑定绘制

本项目使用 `embedded-graphics` crate 作为图形绘制框架。它的核心是 `DrawTarget` trait：

```rust
// embedded-graphics 定义的 trait
pub trait DrawTarget {
    type Color;
    fn draw_iter<I>(&mut self, pixels: I) -> Result<(), Self::Error>
    where I: IntoIterator<Item = Pixel<Self::Color>>;
}
```

`EpdDisplay` 实现了 `DrawTarget`，所以可以使用所有 `embedded-graphics` 的绑定绘制功能：

```rust
// 文字绘制
let style = MonoTextStyleBuilder::new()
    .font(&FONT_6X10)
    .text_color(White)
    .background_color(Black)
    .build();
Text::new("Hello", Point::new(10, 20), style).draw(display);

// 矩形绘制
Rectangle::new(Point::new(0, 0), Size::new(100, 50))
    .into_styled(PrimitiveStyle::with_fill(Black))
    .draw(display);

// 自定义 Widget 绘制
calendar.draw(display);  // 任何实现了 Drawable trait 的组件
```

### 4.3 中文渲染

中文显示是本项目的重要需求。通过 `u8g2-fonts` crate 加载 GB2312 编码的文泉驿点阵字体（内置 wqy12 / wqy14 / wqy16 三档字高，按屏幕尺寸与场景选用）：

```rust
// src/main.rs:270-271
let font: FontRenderer = FontRenderer::new::<fonts::u8g2_font_wqy14_t_gb2312>();
let _font = font.with_ignore_unknown_chars(true);  // 忽略无法渲染的字符
```

`u8g2_font_wqy14_t_gb2312` 是文泉驿字体，支持完整的 GB2312 中文字符集。14 表示字高 14 像素——在 296×128 的小屏幕上，每行约显示 21 个汉字，7 行文字。

使用方式：

```rust
// src/display.rs:366-396（show_sleep，无自定义壁纸时的兜底画面）
```

## 5. 待机壁纸系统

待机壁纸是电子墨水屏的一个巧妙应用——因为断电后画面不消失，待机画面可以作为设备的"外观"。

睡眠画面有两个入口：普通模式走 `display::show_sleep()`；阅读模式通过 `set_sleep_renderer()` 注册了自己的渲染钩子（`SLEEP_RENDERER` 函数指针，存阅读进度 + 电量状态行），有钩子时优先用钩子画，没有才走壁纸路径。

### 5.1 存储位置

壁纸存储在 Flash 的 `storage` 分区（`0x310000` 起始，128KB）：

```rust
// src/flash_sleep.rs:9-18
const STORAGE_OFFSET: u32 = 0x310000;
const SLEEP_IMAGE_MAGIC: u32 = 0x534C4550;
const HEADER_SIZE: usize = 8;

const SLEEP_IMG_W: u32 = 300;
const SLEEP_IMG_H: u32 = 400;
const ROW_BYTES: usize = (SLEEP_IMG_W as usize + 7) / 8;

const DEFAULT_SLEEP_PIXELS: &[u8; ROW_BYTES * SLEEP_IMG_H as usize] =
    include_bytes!("../files/sleep_default.bin");
```

存储格式：8 字节头 + 像素数据。头部包含魔数（`0x534C4550`，即 "SLEP"）和像素数据长度。Flash 里没有有效壁纸时，回退到编译期内置的默认壁纸 `files/sleep_default.bin`。

### 5.2 BMP 转换与缩放

用户上传的 BMP 图片需要转换为屏幕可用的 1-bit 格式，并缩放到目标尺寸：

```rust
// src/flash_sleep.rs:38-109（核心逻辑简化）
pub fn bmp_to_pixels(raw_bmp: &[u8], target_w: u32, target_h: u32) -> Option<AllocVec<u8>> {
    // 解析 BMP 头（支持负高 top-down 行序）
    let bpp = ...; // 支持 1-bit, 24-bit, 32-bit

    // 逐像素缩放
    for dy in 0..target_h {
        let src_y = dy * bmp_h / target_h;  // 最近邻缩放
        for dx in 0..target_w {
            let sx = dx * bmp_w / target_w;
            let is_black = match bpp {
                1 => /* 读取 1-bit 像素（0 为黑） */,
                24 | 32 => {
                    // RGB -> 灰度 -> 二值化
                    let (b, g, r) = ...;
                    (r * 299 + g * 587 + b * 114) / 1000 < 128  // ITU-R BT.601
                },
            };
            // 打包为 1-bit（MSB 在前）
            if is_black {
                pixels[row_offset + idx / 8] |= 1 << (7 - (idx % 8));
            }
        }
    }
}
```

灰度到二值的转换使用 ITU-R BT.601 标准的亮度公式：`Y = 0.299R + 0.587G + 0.114B`，阈值为 128。

### 5.3 流式读取渲染

壁纸图像可能很大（300×400/8 ≈ 15000 字节），为了避免一次性分配大量内存，渲染时逐行从 Flash 读取：

```rust
// src/flash_sleep.rs:219-246
pub fn draw_sleep_image<D>(display: &mut D) -> bool
where
    D: DrawTarget<Color = BinaryColor>,
{
    let mut header = [0u8; 8];
    let has_flash_image = read_flash(STORAGE_OFFSET, &mut header).is_ok()
        && u32::from_le_bytes([header[0], header[1], header[2], header[3]]) == SLEEP_IMAGE_MAGIC;

    if has_flash_image {
        let mut row_buf = [0u8; ROW_BYTES];
        for y in 0..SLEEP_IMG_H {
            let offset = STORAGE_OFFSET + HEADER_SIZE as u32 + y as u32 * ROW_BYTES as u32;
            if read_flash(offset, &mut row_buf).is_err() {
                return false;
            }
            // 逐像素绘制到帧缓冲区
            for x in 0..SLEEP_IMG_W {
                if (row_buf[x / 8] >> (7 - x % 8)) & 1 != 0 {
                    Pixel(Point::new(x as i32, y as i32), BinaryColor::On).draw(display);
                }
            }
        }
    } else {
        draw_pixels(display, DEFAULT_SLEEP_PIXELS, SLEEP_IMG_W, SLEEP_IMG_H);
    }
    true
}
```

每次只读一行（38 字节），内存占用极低。

### 5.4 崩溃安全写入

壁纸写入采用"先清头部、写数据、再写有效头部"的三步策略：

```rust
// src/flash_sleep.rs:195-217
pub fn save_sleep_image(raw_bmp: &[u8]) -> Result<(), &'static str> {
    let pixels = bmp_to_pixels(raw_bmp, SLEEP_IMG_W, SLEEP_IMG_H).ok_or("invalid BMP")?;

    // 步骤 1：清除头部（标记为无效）
    write_flash(STORAGE_OFFSET, &zero_header)?;

    // 步骤 2：写入像素数据
    write_flash(STORAGE_OFFSET + HEADER_SIZE as u32, &pixels)?;

    // 步骤 3：写入有效头部（标记为有效）
    header[0..4].copy_from_slice(&SLEEP_IMAGE_MAGIC.to_le_bytes());
    header[4..8].copy_from_slice(&(total_size as u32).to_le_bytes());
    write_flash(STORAGE_OFFSET, &header)?;

    Ok(())
}
```

如果在写入像素数据过程中断电，重启后头部是无效的（全零），系统会使用默认壁纸。只有完整写入后才将头部标记为有效。这是一种简单但有效的崩溃安全策略。Web 上传大图时走的是同一策略的分步版本（`begin_sleep_image_write` → 逐行 `write_sleep_pixel_row` → `finish_sleep_image_write`），避免一次性持有整张图的缓冲。

## 6. 渲染流水线总结

完整的渲染流水线如下：

```
用户操作 / 定时器
      │
事件派发（dispatch 任务 → 页面事件回调）
      │
修改页面状态
      │
display_mut() → 获取帧缓冲区（static mut）
      │
embedded-graphics API 绑定绘制
(Text / Rectangle / Widget / Font)
      │
RENDER_CHANNEL.send(RenderInfo)
      │（异步 Channel，不阻塞）
      │
render task 接收请求，RENDER_BUSY=true
      │
检查屏幕是否在睡眠 → wake_up()
      │
检查刷新计数 / NEED_CLEAR → 是否需要全刷
      │
epd.update_and_display_frame(buffer)
      │（通过 SPI 发送到屏幕）
      │
wait_refresh_done() — 每 2ms 轮询 BUSY，
期间让出 executor 给其它任务
      │
检查 need_sleep → 是否让屏幕睡眠
      │
RENDER_BUSY=false → Timer::after(50ms)，继续循环
```

睡眠路径在断电前还会调用 `await_render_idle()` 等 RENDER_BUSY 清零、队列排空，避免把面板留在刷新中途。

## 小结

| 技术点 | 要点 |
|--------|------|
| 屏幕驱动 | epd-waveshare（自定义 fork）+ 条件编译适配多尺寸，屏型/板型 feature 编译期守卫 |
| 渲染架构 | 生产者-消费者模式，Channel 解耦页面与硬件 |
| 异步刷新 | 驱动发命令后异步等 BUSY（wait_refresh_done，2ms 轮询让出 CPU）；睡眠/断电前 await_render_idle 排空 |
| 刷新策略 | 每 N 次快刷强制全刷清残影；N 运行时可配（DisplayStorage，钳制 1..=100），RTC 保持计数；冷启动/按键唤醒首帧强制全刷（NEED_CLEAR） |
| 2.7 寸特殊处理 | PREV_BUFFER 帧备份，唤醒后静默过渡；计数达到 N 用 set_base_map 重建基准并归零 |
| 帧缓冲区 | 1-bit 二值图，通过 core::ptr 全局访问 |
| 图形绘制 | embedded-graphics DrawTarget + u8g2 文泉驿点阵中文渲染（wqy12/14/16） |
| 待机壁纸 | Flash 存储 + BMP 转换 + 流式渲染 + 崩溃安全；阅读模式可注册自定义睡眠渲染钩子 |

核心设计思想：**将耗时的硬件操作封装在独立任务中，通过异步 Channel 解耦，让页面代码专注于业务逻辑而非硬件细节**。
