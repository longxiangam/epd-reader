# 第 9 篇：错误处理与调试

> English: [en/09-error-handling-and-debugging.md](en/09-error-handling-and-debugging.md)

> 用 Rust 构建ESP32-C3 电子墨水屏阅读器 · 系列文章

## 引言

在嵌入式开发中，调试是一件痛苦的事情。没有 GDB 的时候，你只能靠 `printf` 大法；设备突然重启了，你不知道为什么；程序崩溃了，你连调用栈都看不到。

本项目的错误处理系统通过自定义 Panic Handler、Flash 错误日志、调用栈回溯三层机制，让"黑盒"设备也能提供有价值的调试信息。

## 1. 自定义 Panic Handler

Rust 在 `#![no_std]` 环境中没有默认的 panic 处理。你必须自己实现 `#[panic_handler]`：

```rust
// src/panic.rs:9-100（节选）
#[panic_handler]
fn panic_handler(info: &PanicInfo) -> ! {
    println!("!! 发生panic错误 !!");

    // 1. 构建错误信息
    let mut error_msg = heapless::String::<200>::new();

    // 文件位置：file:line:column
    if let Some(location) = info.location() {
        let _ = error_msg.push_str("location: ");
        let _ = error_msg.push_str(location.file());
        let _ = write!(error_msg, ":{}:{}", location.line(), location.column());
        let _ = error_msg.push_str("\n");
    } else {
        let _ = error_msg.push_str("location: unknow\n");
    }

    // panic 消息
    let _ = error_msg.push_str("error: ");
    let _ = write!(error_msg, "{}", info.message());
    let _ = error_msg.push_str("\n");

    // 2. 捕获调用栈
    let _ = error_msg.push_str("stack:\n");
    let backtrace = Backtrace::capture();
    let mut stack_count = 0;
    for frame in backtrace.frames() {
        if stack_count < 10 {   // 限制调用栈深度为 10 层
            let _ = write!(error_msg, "  #{} 0x{:x}\n", stack_count, frame.program_counter());
            stack_count += 1;
        } else { break; }
    }
    if stack_count == 0 {
        let _ = error_msg.push_str("call stack information is not available\n");
    }
    if error_msg.len() > 200 { error_msg.truncate(200); }  // 与存储字段等宽

    // 3. 保存到 Flash（读失败则用默认值，保证 panic 时一定能写）
    let mut error_storage = match ErrorLogStorage::read() {
        Ok(storage) => storage,
        Err(_) => ErrorLogStorage::default(),
    };
    error_storage.error_count += 1;
    error_storage.last_error = error_msg;   // 直接保存新错误，不保留旧消息
    let _ = error_storage.write();

    // 4. 打印完整错误到串口
    println!("错误计数: {}", error_storage.error_count);
    println!("最后错误: {}", error_storage.last_error);

    // 5. 等待 Flash 写入完成
    for _ in 0..1000000 {
        core::hint::spin_loop();
    }

    // 6. 停机（software_reset 被注释掉了——需要人工介入）
    loop { }
}
```

### 关键设计决策

**为什么不自动重启？** 代码最后是 `loop {}` 而不是 `software_reset()`（重启那行被注释掉了，虽然日志里仍打印"系统将重启"）。这是故意的——如果 panic 后自动重启，可能会陷入崩溃循环（不断 panic → 重启 → panic），而且重启会覆盖 `last_error`，让你永远看不到第一现场。让设备停在 panic 状态，可以通过串口看到完整的错误信息，复位后再在 DebugPage 里回看。

**为什么用 `spin_loop()` 等待？** Panic handler 中不能使用异步操作（`.await`），也不能使用阻塞延时（需要硬件定时器）。`spin_loop()` 是一个忙等待循环，作为 CPU 空操作提示，让 Flash 写入有时间完成。

**防御式写入**：`ErrorLogStorage::read()` 失败（例如 Flash 尚未初始化就 panic）时改用 `ErrorLogStorage::default()`，保证错误信息总能落盘；错误串在写入前截断到 200 字符，与 `last_error: String<200>` 字段严格等宽，不会静默截断出半截 UTF-8。

## 2. 调用栈回溯

### 2.1 Backtrace 捕获

`esp-backtrace` crate（0.19）提供了 RISC-V 架构的栈回溯能力：

```rust
// src/panic.rs:40-49
let backtrace = Backtrace::capture();
for frame in backtrace.frames() {
    let _ = write!(error_msg, "  #{} 0x{:x}\n", stack_count, frame.program_counter());
}
```

esp-hal v1.x 使用 `Backtrace::capture()` 返回结构化的回溯对象，通过 `.frames()` 迭代获取每一帧的程序计数器（PC）地址。旧版直接返回 `[Option<u32>; 10]` 数组。若一个帧都没采到（帧指针链断裂），会明确写入 "call stack information is not available"，避免误判为"没有崩溃"。

### 2.2 帧指针的支持

回溯能力依赖帧指针（frame pointer），在编译选项中启用：

```toml
# .cargo/config.toml
rustflags = [
  "-C", "link-arg=-Tlinkall.x",
  "-C", "force-frame-pointers",
]
```

帧指针是函数调用栈的"链表"——每个栈帧开头保存了上一个栈帧的地址。通过沿着帧指针链回溯，就能得到完整的调用栈。Rust 默认会在优化时省略帧指针以节省一个寄存器，`force-frame-pointers` 强制保留。

### 2.3 地址解析

捕获到的 PC 地址如 `0x42001234` 是裸地址。要解析到函数名和源码位置，需要用到编译产物中的 ELF 文件：

```bash
# 使用 addr2line 解析地址
riscv32-esp-elf-addr2line -e target/riscv32imc-unknown-none-elf/release/epd-reader 0x42001234
```

这会输出类似 `src/wifi.rs:123` 的结果。虽然不能在设备上直接做这个解析，但通过串口日志记录地址，事后分析时可以精确定位崩溃位置。

## 3. 错误日志持久化

### 3.1 存储结构

```rust
// src/storage.rs:168-172
#[derive(Debug, Default, Clone)]
pub struct ErrorLogStorage {
    pub error_count: u32,
    pub last_error: heapless::String<200>,
}
```

错误日志存储在 Flash 的 NVS 分区（第 6 篇的存储链第 7 块），包含：
- `error_count`：累计 panic 次数
- `last_error`：最近一次 panic 的详细信息（位置 + 消息 + 最多 10 帧调用栈，共 200 字符）

### 3.2 启动时检查

如果启用了 `enable_debug` feature，启动时会检查是否有错误日志：

```rust
// src/pages/main_page.rs:93-103
#[cfg(feature = "enable_debug")]
if let Ok(error_log) = crate::storage::ErrorLogStorage::read() {
    if error_log.error_count > 0 {
        println!("=== 检测到错误日志，进入调试模式 ===");
        println!("错误计数: {}", error_log.error_count);
        println!("最新错误信息:");
        println!("{}", error_log.last_error);
        println!("================================");
        page_index = 5;  // 直接进入 DebugPage
    }
}
```

这样开发者可以在重启后通过 DebugPage 查看上次崩溃的详细信息。检查放在 `MainPage::init` 里、默认主页选择之后；注意它写在 NVS"恢复最后所在页"之前——若 Flash 里存有有效的页码记录，恢复值会覆盖 `page_index = 5`，调试页只在无有效页记录（冷启动/首次崩溃）时真正弹出，串口日志则始终会打印错误内容。

## 4. DebugPage

DebugPage 提供了一个简单的界面来查看错误日志，并支持清除操作：

- **Key1 长按（松开）**：清除错误日志（`error_count = 0`，`last_error` 清空）并重绘
- **Key3 短按**：退出 DebugPage

它的 `render()` 方法每次重绘前都重新 `ErrorLogStorage::read()`，把 `last_error` 用 `embedded-text` 的 `TextBox` 分行绘制到屏幕上（wqy12 点阵字体）；没有错误时显示"没有错误日志"。

## 5. 串口调试

### 5.1 esp-println

```rust
use esp_println::println;
println!("wifi connected: {:?}", state);
```

`esp-println` 通过 UART 输出调试信息。在 `cargo run` 时，`espflash monitor` 会自动打开串口监视器，所有 `println!` 输出都会显示在终端中。

### 5.2 log 框架

项目同时启用了 `log-04` feature，可以使用 `log` crate 的分级日志：

```rust
use log::trace;
trace!("test trace");  // 只有启用了 log 的项目才输出
```

`log` 框架支持 `error!`、`warn!`、`info!`、`debug!`、`trace!` 五个级别，可以在编译时过滤不需要的日志级别，减少串口输出量。

### 5.3 运行期诊断打印

除了错误路径，代码里还埋了几组周期性"体检"打印，按 `[tag]` 前缀归类：

**电池 `[bat]`**——电池采样任务每 60 秒读一次 ADC，成功后打印一行换算诊断：

```rust
// src/battery.rs:69-73
// pin = 11dB 衰减理论满量程下的引脚电压估计；bat = raw×2 估的电池电压
// （两者差 2 倍即分压比），供与万用表实测分压中点对比
println!("[bat] raw={} pin≈{}mV bat≈{}mV 电量{}%", adc_value, pin_mv, v.voltage, v.percent);
```

ADC 偶发读数失败会重试：每次间隔 2ms，最多 50 次（`tries >= 50` 放弃本轮，保留上次电量，同时防止死循环期间一直持锁）；电量 < 20% 时额外打印低电警告。采出的百分比还会写进 rtc_fast 的 `LAST_BATTERY_PERCENT`，渲染路径可以用 `battery::last_percent()` 同步读取、无需 await。分压脚按板型选择：v2 新板 GPIO2、旧板 GPIO4（`crate::board::BatAdcGpio`）。

**板级启动诊断 `[diag]`**——`board::print_boot_diag()` 每次调用把 rtc_fast 里的 `RTC_FAST_BOOT_SEQ` 自增并打印：

```rust
// src/board/mod.rs:82-94（节选）
pub fn print_boot_diag() {
    let (when_ts, clk_sync) = crate::worldtime::diag_rtc_fast();
    // boot_seq 跨深睡递增 = rtc_fast 保留正常；归 1 = 深睡中丢失
    println!("[diag] rtc_fast boot_seq={} when_sleep_ts={} clk_sync={}", ...);
}
```

配合 `worldtime::diag_rtc_fast()`（转储睡前时间戳与对时标志），一条日志就能判断"这次唤醒 rtc_fast 到底保没保住"——这是排查深睡唤醒分类问题（定时唤醒 vs 按键唤醒）的第一手证据。串口里还有 `[wake]`（唤醒原因 + 天气是否过期）、`[time]`（时间从 PCF8563 恢复/写回）、`[sd]`（SD 卷打开结果）、`[page]`（本次进入的页面）等标签，同一风格。

## 6. 常见错误模式

### 6.1 unwrap() panic

嵌入式代码中大量使用 `unwrap()`：

```rust
let mut epd = EpdControl::new(...).unwrap();
spawner.spawn(display::render(...)).unwrap();
```

如果 `EpdControl::new` 失败（如 SPI 通信错误），程序会 panic。Panic handler 会记录到 Flash，下次启动可以在 DebugPage 中看到。

### 6.2 栈溢出

ESP32-C3 的主 DRAM 现在全部留给调用栈（堆被挪去了独立的 dram2 段，见 6.3），异步任务链深时栈上仍然可能出现大局部变量。项目的对策有两个：大的结构体分块处理——`HolidayStorage` 的分块写入（第 6 篇）每次只上栈 128 字节；以及 `_stack_end` 处的看门狗 watchpoint，溢出即刻捕获而不是静默踩坏堆。

### 6.3 内存不足

堆被放在 bootloader 释放的 ~64KB dram2 段（`esp_alloc::HEAP.add_region`），主 DRAM 整段让给栈——堆栈互不挤压。但 64KB 仍要精打细算：HTTP/TLS 的 ~33KB 大缓冲放在 `.bss` 由 `WIFI_LOCK` 串行化独占，不占堆；需要堆分配的地方（如解析 JSON、页面菜单）要控制峰值。`esp-alloc` 在内存不足时返回分配失败，相关 `unwrap()`/`expect()` 就会 panic。

## 7. 调试工具链

| 工具 | 用途 |
|------|------|
| `espflash monitor` | 串口监视器，查看 `println!` 输出 |
| `addr2line` | 将 PC 地址解析为源码位置 |
| `esp-backtrace` | RISC-V 调用栈回溯 |
| `enable_debug` feature | 启动时自动进入调试页面 |
| Flash 错误日志 | Panic 信息持久化，重启后可查看 |
| `[bat]`/`[diag]` 等诊断打印 | 电池换算、rtc_fast 保留状态、唤醒原因 |

## 小结

| 技术点 | 要点 |
|--------|------|
| Panic Handler | 自定义处理，位置+消息+10 帧调用栈写入 Flash |
| Backtrace | `force-frame-pointers` + `esp-backtrace` 0.19 |
| 错误日志 | Flash 持久化，重启后可在 DebugPage 查看/清除 |
| 串口调试 | `esp-println` + `log` 框架 + `[bat]`/`[diag]` 诊断打印 |
| 内存布局 | 堆在 dram2 段、主 DRAM 全栈、HTTP 缓冲在 `.bss` |
| 地址解析 | 事后用 `addr2line` 将 PC 地址映射到源码 |

嵌入式调试的核心挑战是**信息不足**——你无法attach 调试器，无法实时查看变量。本项目的策略是：**尽可能多地捕获和保存崩溃信息**，让事后分析成为可能。
