# 第 11 篇：固件镜像构建与烧录 — 从 ELF 到 .bin

> 用 Rust 构建ESP32-C3 电子墨水屏阅读器 · 系列文章

## 引言

日常开发时，`cargo run --release --features epd4in2` 一条命令就能编译 + 烧录 + 打开串口监视器——espflash 拿到的是 ELF 文件，自己完成格式转换。但总有 ELF 不够用的场景：给别人发一个固件文件、用 esptool/web 烧录器烧录、做整机出厂镜像。这时就需要把构建产物转成 `.bin` 固件镜像。

本文讲清楚三件事：ELF 和 bin 的关系、ESP 固件镜像的格式原理、本项目两种 bin（整片镜像 / 仅应用）的生成与烧录命令。

## 1. 构建产物：ELF 里有什么

```bash
cargo build --release --features epd4in2
```

产物是 `target/riscv32imc-unknown-none-elf/release/epd-reader`——一个 RISC-V 架构的 ELF 文件。它包含：

- **可加载段**：`.text`（代码）、`.rodata`（常量/字体表）、`.data`/`.bss`（数据）——这些是真正要进 flash 的内容；
- **调试信息**：符号表、DWARF 行号信息——只给调试器/addr2line 用，不进 flash。

espflash 烧录 ELF 时自己解析段表、丢掉调试信息、套上 ESP 镜像格式头。`.bin` 就是把"套好头的可加载段"落成文件，脱离 espflash 也能被任何烧录工具识别。

## 2. ESP 固件镜像格式原理

### 2.1 镜像头与段表

ESP32 系列的固件镜像（无论 bootloader 还是应用）都是同一种格式，文件首字节固定为魔数 `0xE9`：

```
E9 | 段数 | SPI 模式 | SPI 大小/频率 | 入口地址 4B | 扩展头 | 段表 N × (地址, 长度) | 段数据... | SHA256
```

bootloader 上电后逐段搬运：`DROM`/`FLASH` 段留在 flash 由 MMU 映射，`IRAM`/`DRAM` 段复制到 RAM，最后跳到入口地址。末尾附 32 字节 SHA256 供校验。

应用镜像的扩展头里还有一段 `esp_app_desc`——本项目 `main.rs` 里的 `esp_bootloader_esp_idf::esp_app_desc!()` 就是往这里填项目名与版本号，`esptool image_info` 和 espflash 读到的版本信息都来自它。

### 2.2 二级引导与分区表

ESP32-C3 的 flash 布局由两级构成：

1. **一级引导**（ROM 内固化）：上电复位向量，只负责把 flash 0x0 处的二级引导加载到 RAM 执行；
2. **二级引导**（bootloader，烧在 0x0）：解析 0x8000 处的**分区表**，找到 type=app 的分区，按上面的镜像格式校验并启动应用。

本项目 `partitions.csv` 里各分区的 Offset 列留空，espflash/IDF 按约定自动分配，最终布局：

```
0x00000  二级引导 bootloader        (~28KB)
0x08000  分区表                    (4KB)
0x09000  nvs      data/nvs         (24KB)   ← WiFi 凭据 + 全部 *Storage 设置
0x0F000  phy_init data/phy         (4KB)
0x10000  factory app  type=app     (3MB)    ← 应用镜像烧这里
0x220000 前面用满后 ... storage data/fat (128KB) ← 书籍进度等 SD 之外的数据
```

**关键点**：`nvs` 和 `storage` 两个数据分区夹在引导区和应用区之间/之后。整片镜像烧录会把这些区域一并覆盖——这就是"整片镜像 = 数据清空"的根源。

## 3. 生成命令

### 3.1 整片合并镜像（bootloader + 分区表 + 应用）

```bash
cargo build --release --features epd4in2
espflash save-image --chip esp32c3 --partition-table ./partitions.csv \
  --merge --flash-size 4mb \
  target/riscv32imc-unknown-none-elf/release/epd-reader \
  dist/epd-reader-merged.bin
```

`--merge` 把二级引导（espflash 内置的 ESP-IDF bootloader）、分区表、应用镜像按各自偏移拼成一个与整片 flash 等大的文件（4MB，含 0xFF 填充）。输出末尾的 `App size` 一行会给出应用实际大小，本项目当前约 2.1MB，占 factory 分区 68%。

### 3.2 仅应用镜像（保数据）

合并镜像里应用固定起始于 `0x10000`，用 `tail`/`head` 直接裁出这一段：

```bash
tail -c +$((0x10000+1)) dist/epd-reader-merged.bin | head -c 2140640 > dist/epd-reader-app.bin
```

- `tail -c +N` 从第 N 字节开始（1 基），所以是 `0x10000+1`；
- `head -c` 截到应用实际大小为止，不把后面的 0xFF 填充和 storage 分区带进来；
- **大小数字随代码变动，以 save-image 输出的 `App size` 为准**。

裁出来的文件以 `0xE9` 开头，就是标准应用镜像，烧到 factory 分区偏移即可，**nvs（WiFi/全部设置）与 storage（书籍数据）原样保留**。

## 4. 烧录命令

```bash
# 日常更新（保数据，推荐）
espflash write-bin 0x10000 dist/epd-reader-app.bin --chip esp32c3

# 整机镜像（清空全部数据，仅换板/出厂分发用）
espflash write-bin 0x0 dist/epd-reader-merged.bin --chip esp32c3

# 等价的 esptool 写法
esptool --chip esp32c3 write_flash 0x10000 dist/epd-reader-app.bin

# 日常开发仍走 runner（ELF 直烧 + 串口监视）
cargo run --release --features epd4in2
```

## 5. 注意事项

- `dist/` 产物不入库（构建产物），`epd-reader-merged.bin` 恒为 4MB——它不是"固件有 4MB"，而是"与整片 flash 等大"；
- 烧 `epd-reader-app.bin` 前无需手工擦除，esptool/espflash 写入时自动擦对应扇区；
- 两个 bin 都依赖 `--features epd4in2`：换屏型（2in7/2in9）要重编，镜像不通用；
- `--flash-size` 必须与实际 flash 容量一致（本板 4MB），合并镜像才能保证填充边界正确。
